# ADR-0003 — Bot token custody, connect / rotate / disconnect flow

- Status: accepted
- Date: 2026-10-22
- Related: ADR-0002, DOMAIN_CONTRACT §3.1 `telegram_bots`, §4.5 (bot state machine), §7.2, §9.1, §14

## Context

A BotFather token is a full credential: whoever holds it can read every message employees send.
PLATFORM says web never talks to Telegram directly, yet the admin needs immediate feedback in the
onboarding wizard ("token is wrong" vs "connected as @CleanTeamHelpBot"). A naive design passes the
token through the outbox (`jsonb` in Postgres) or BullMQ job data (Redis, Bull Board, logs).

## Decision

### Storage
- `public.telegram_bots.token` and `.webhook_secret` use Laravel `encrypted` casts (APP_KEY). The token
  is never returned to the browser (UI shows `…` + last 4 chars of the secret part and the bot username).
- `webhook_secret`: 32 chars from `[A-Za-z0-9_-]`, generated by web on every connect/rotation.
- `tg_bot_id` = numeric part of the token before `:`; it is known before calling Telegram, so the
  uniqueness check is local: partial unique index `telegram_bots_tg_bot_id_live` on `(tg_bot_id)`
  `WHERE status <> 'disconnected'`. A second workspace claiming the same bot gets `already_connected`
  (localized: "This bot is already connected to another OpsBot workspace").

### Connect (synchronous, immediate feedback)
1. `POST /bot {token}` (permission `bot.manage`). Format check `^\d{5,16}:[A-Za-z0-9_-]{30,64}$`.
2. Web upserts the workspace's row: status `connecting`, token, new secret, `connected_by`.
3. Web calls the worker **synchronously**: `POST {WORKER_URL}/internal/v1/telegram/bots/{id}/verify`
   (signed per PLATFORM §4.1, timeout 15 s).
4. Worker fetches credentials: `GET {WEB_URL}/internal/v1/telegram/bots/{id}/credentials` (signed) →
   `{bot_key, tg_bot_id, username|null, token, webhook_secret, status}`. Served only for status
   `connecting | active | revoked | disconnecting`; otherwise `410`.
5. Worker: `getMe` (401 → `invalid_token`; `getMe.id ≠ tg_bot_id` → `token_mismatch`; timeout/5xx →
   `network`), then `setWebhook({WORKER_PUBLIC_URL}/webhooks/telegram/{bot_key}, secret_token,
   allowed_updates)` in webhook mode, or starts the polling loop in dev (`TELEGRAM_MODE=polling`), or
   nothing for the fake transport; then `setMyCommands` for `ru` and default (`en`).
   `setWebhook` failure → `webhook_failed` (hint: `WORKER_PUBLIC_URL` must be public HTTPS).
6. Worker answers `{ok:true, tg_bot_id, username, first_name, mode:'webhook'|'polling'|'fake'}` or
   `{ok:false, error_code}`; it never echoes the token.
7. Web: on success → status `active`, `username`, `last_seen_at`, audit `telegram_bot.connected`;
   on `invalid_token|token_mismatch` → status `invalid_token` + `last_error`; on
   `network|webhook_failed` → stays `connecting`, UI shows retry. The page re-renders with the result.

### Rotate (BotFather `/revoke`)
- `PATCH /bot/token {token}` runs the same verify. **Same `tg_bot_id`** → links and chats stay valid
  (same bot, same users), audit `telegram_bot.token_rotated`, worker registry evicted via pub/sub.
- **Different `tg_bot_id`** → treated as disconnect + connect: old links are dropped (see below) and
  the employees page shows "N employees need a new invite link" with a bulk "Regenerate links" action.

### Disconnect (asynchronous, reliable)
1. `DELETE /bot` (confirm dialog) → status `disconnecting`, audit `telegram_bot.disconnect_requested`,
   outbox `telegram.bot.disconnect {bot_key, telegram_bot_id, workspace_id}`.
2. Worker handler: credentials → `deleteWebhook(drop_pending_updates=true)` (or stop polling) →
   delete `worker.telegram_chats` rows of that `bot_key` → publish registry eviction →
   `POST /internal/v1/telegram/bots/{id}/status {status:'disconnected'}`.
3. Web on `disconnected`: wipes `token` and `webhook_secret` (set NULL), deletes `telegram_accounts`
   rows of the bot, revokes unused `employee_links`, audit `telegram_bot.disconnected`.
   If the worker gives up (5 attempts) web still finalizes on the next daily tick and logs a warning;
   Telegram then receives `404` from `/webhooks/telegram/{bot_key}` and stops.

### Runtime health
- Worker reports `POST /internal/v1/telegram/bots/{id}/status`: `revoked` when Telegram answers `401`
  for an active bot (token revoked in BotFather) — admins get an e-mail + dashboard banner; `active`
  with `last_seen_at` at most every 10 min while updates flow.

### Secrets never leave the custody path
- No token in outbox payloads, job data, logs, Bull Board, error messages or Telegram messages.
  - `assertNoSecrets(data)` in the worker enqueuer and in web `Outbox::publish` rejects keys named
    `token`, `bot_token`, `api_key`, `secret`, `webhook_secret`, `password` (case-insensitive, any depth)
    and any string value matching `^\d{5,16}:[A-Za-z0-9_-]{30,}$`. Unit-tested on both sides.
    The employee deep-link token is never put in the outbox either (shown in the UI only).
  - pino `redact` paths for `*.token`, `*.webhook_secret`, and a serializer that rewrites
    `bot\d+:[A-Za-z0-9_-]+` (grammY puts the token in API URLs) to `bot<redacted>`. Vitest asserts a
    thrown grammY error is logged without the token.
- Credentials endpoint is signed, rate-limited (`internal` limiter) and logged at info level without
  the secret values.

### Offline / tests
- `FakeTelegramDriver` (worker): tokens matching `^\d+:TEST[A-Za-z0-9_-]{30,}$` always use the fake
  transport: `getMe` returns `{id: <prefix>, is_bot: true, first_name: 'Test Bot <prefix>',
  username: 'test_<prefix>_bot', can_join_groups: false}`; every outbound call is captured
  (`/dev/telegram/outbox?bot_key=`). `TELEGRAM_DRIVER=auto|fake` (`fake` forces the fake transport for
  all tokens — used in CI). E2E connects a bot with `123456789:TEST` + 30 safe chars.

## Consequences

- The wizard gets a definitive answer in < 15 s; disconnect survives worker restarts.
- A database dump without APP_KEY does not expose bot tokens.
- Two places can trigger Telegram calls for a company bot (verify endpoint and job handlers) — both
  live in the worker; web still never calls Telegram.

## Alternatives rejected

- **Token in the outbox payload** — plaintext in `outbox_messages` and Redis; rejected.
- **Worker stores tokens in its own schema** — two sources of truth for bot status; rotation races.
